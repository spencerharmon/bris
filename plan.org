#+TITLE: Bris Development Plan
#+STARTUP: overview

Step-by-step plan to build Bris from scratch. Phases are roughly sequential
but later phases can begin once their dependencies in earlier phases are
stable. Each task is sized to a meaningful unit of work, not a single commit.

* Decisions baked in
- *License:* GPL-3.0. ~cargo-deny~ enforces license-compatible deps from
  the first commit.
- *Repo structure:* monorepo. May split later if mobile teams want
  independent CI cadence.
- *Rust toolchain:* current stable. Pi Zero 2W is aarch64 and fully
  supported.
- *Accuracy target:* "best we can do" is the design philosophy. Baseline
  design target ≈1–2 nm (ocean passage); 0.5 nm is a stretch contingent
  on validation data. The user never sees these targets — they see the
  actual numeric uncertainty per fix and configure their own accept
  threshold.
- *Config:* TOML. ~/etc/bris/config.toml~ for system, ~~/.config/bris/config.toml~
  for unprivileged user override. XDG-style per-key shadowing.
- *Star catalog:* Yale BSC (~9000 stars, <1 MB) for the general catalog;
  the 57 standard navigational stars are cross-referenced to Hipparcos
  IDs for accurate proper motion. Catalog-induced fix error is negligible
  at any of these levels.
- *Sight database:* SQLite, used for the log on both mobile and embedded.
- *Process model:* one binary per device, no daemon/client split. The
  Rust core is in-process with the frontend (CLI on embedded, UniFFI
  library call on mobile).
- *Hardware product future-proofing:* factory-default calibration baked
  into device images, persistent device UUID, factory-reset = wipe
  overlay. Doesn't change architecture.
- *Updates:* mobile via app store updates. Embedded via user-initiated
  ~bris-cli update~ command. The same update channel carries leap-second
  table, almanac coefficients, and star catalog as a single ~bris-data~
  payload, signed and atomically swapped. Leap-second updates have a
  hard operational deadline (an announced leap second must be applied
  before its effective UTC instant); almanac/catalog updates do not.
  Auto-update infrastructure deferred until a hardware product justifies
  the operational complexity.
- *No telemetry, no analytics, no automatic network calls.*

* Crucial findings (validated against real footage)
This section captures algorithm-level findings that have been
empirically validated against captured frames in
~test_video/~. These are not design assumptions — they are
observations from running the pipeline against real data, with
references to the regression tests that pin the behavior. See
~progress.md~ for the per-scene inventory.

** Horizon detection on cluttered shipboard scenes requires ML
   Both classical detectors (gradient and sky-region) fail on the
   typical sailing-camera scene where the deck and sail occupy the
   lower half of the frame. The gradient detector picks a
   deck-to-sea boundary as its strongest horizontal edge; the
   sky-region detector picks the top of the mainsail.

   The ML segmentation detector (SegFormer-B0 / ADE20K) cleanly
   separates sky / sea / boat / ship pixels and finds 172 of 512
   columns with clean sky→sea transitions on the
   ~sailing_sun_upper_left~ regression scene. This is the only
   approach that works on real shipboard footage.

   Implication: the production system must ship the segmentation
   model. Classical detectors remain available as fast-path options
   for clean open-ocean scenes where they're equally accurate, but
   they cannot be the only horizon detector.

** Obstruction-aware horizon doubles available evidence on real scenes
   The ~sailing_with_distant_shore~ regression scene has a distant
   shoreline visible between sea and sky on the right. Strict
   sky→sea-only matching finds 162 candidate columns. The
   obstruction-aware variant adds 168 more by walking past the
   shore band looking for sea below it — total 330 of 512.

   The shore band is treated as a horizon proxy at the
   sky→shore transition row. When weighted RANSAC lands (currently
   the SkyToObstructionToSea source is treated identically to
   SkyToSea in RANSAC), the latter source's σ contribution will be
   inflated to reflect lower confidence.

** Sky-mask centroiding has a brightness-bias failure mode (resolved)
   Restricting the centroid search to a sky mask correctly excludes
   non-sky distractors (sun glare on water, sail glare). However,
   when the bright sky region near a saturated body has its own
   internal brightness gradient (haze on one side, deck on the
   other), the area-weighted centroid is pulled toward the brighter
   side of the *sky region*, not the body's actual peak.

   Documented in ~tests/regression/sailing_sun_upper_left/~: visually
   correct Sun is at ~(99, 48); unmasked centroid lands at (99, 48)
   "by accident" because the saturated Sun is the strongest signal
   anywhere in the frame; sky-masked centroid lands at (122, 64).

   *Resolution:* ~centroid_saturated_body_in_mask~ thresholds at an
   absolute saturation level (default 95% of u16::MAX) instead of
   a fraction of the frame's brightest pixel, isolating the body's
   saturated disk. Lands at (99, 45) on this scene — sub-pixel
   close to the visual sun. The function takes an *optional* mask
   for explicit exclusion of competing saturated regions, but the
   typical correct use is unmasked: saturation thresholding alone
   excludes most non-body pixels.

   *Surprise:* the ADE20K segmentation model classifies the
   saturated Sun as *not sky*, so constraining the saturated
   centroider to the sky mask actively excludes the body. The
   unmasked path is the recommended default; a Bris-trained
   segmentation model with a "sky-or-bright-body" class would
   resolve this if/when needed.

** Camera calibration is currently the dominant absolute-altitude error
   Every test uses ~Intrinsics::placeholder(w, h)~ which sets
   fx = fy = 1000. Real wide-angle cameras (GoPro-style at 640×360)
   have fy more like 350-500. Reported altitudes are off by a factor
   of ~2-3 from sky-space truth, even when the horizon and body
   pixel positions are correct.

   This is calibration, not algorithm. The lens-calibration workflow
   (Phase 2 TODO) is required before any absolute altitude reading
   is meaningful. Until then, the regression tests assert pixel-space
   behavior (centroid x/y, horizon slope/intercept, candidate
   counts), not sky-space altitude.

** Single-LOP sights need an assumed position
   This is geometry, not a bug. One body sight gives a line of
   position, not a point. The streaming engine (Phase 3.5) will
   accumulate ≥ 2 azimuth-diverse sights into a real fix; until
   then ~bris replay~ synthesizes a perpendicular zero-intercept
   anchor and labels the result "advisory."

** Horizon and body detection run per-frame, not on a stitched panorama
   The panorama path
   (~bris-vision::panorama::panorama_altitude~) selects the best
   per-frame horizon detection and the best per-frame body
   centroiding across all input frames; if those came from
   different frames, it computes a rigid-transform chain to
   project the body's pixel into the horizon frame's coordinates.

   Implication: the single-frame fast path (body and horizon both
   visible in one frame) is dramatically cheaper than the chain. A
   wide-FOV camera that gets both in one frame doesn't need
   stitching at all. A telephoto camera at high body altitude
   *requires* the chain because no single frame can contain both.

** Night algorithms don't exist yet
   The peak detector handles per-star detection. Plate solving
   (star identification) is not implemented. Night horizon
   detection is not implemented — there's no daylight contrast for
   the existing detectors to find. The user's
   ~night_test_lowres~ footage is the highest-priority test case
   for the next round of algorithm design.

** DONE Annual aberration (classical, Meeus Ch. 23)
   ~apply_annual_aberration~ in ~crates/bris-almanac/src/apparent.rs~.
   Earth heliocentric velocity from numerical derivative of VSOP87D over
   ±30 s, classical v/c formulation, applied between nutation and
   topocentric parallax. ~20″ maximum shift.
** DONE Diurnal aberration (Meeus Ch. 23)
   ~apply_diurnal_aberration~ in ~crates/bris-almanac/src/apparent.rs~.
   Observer's rotational velocity ~v = ω × r~ applied via the same
   classical aberration formula, inserted after topocentric parallax and
   before refraction in the apparent-place chain. Peak ~0.32″ at the
   equator on the meridian, vanishing at the poles. Only the topocentric
   ~body_apparent_place~/~star_apparent_place~ paths apply it;
   ~body_geocentric_apparent~ deliberately does not. Combined annual +
   diurnal aberration residual σ dropped from 0.5″ to 0.15″.

* Phase 1.5: Time integrity
  Offshore operation without NTP for weeks at a time is a primary use case.
  The system clock keeps running, but several failure modes need explicit
  handling.
** TODO Dual-clock timestamping
   Every captured frame carries both a monotonic timestamp (immune to wall-
   clock steps) and a wall-clock timestamp. Fix computation uses monotonic
   deltas within a session and only converts to wall time at the end.
** TODO Clock-step detection
   Watch for wall-clock jumps that disagree with the monotonic clock by more
   than a configurable threshold (e.g. 2 s). On detection: invalidate any
   in-flight sight session and log the event. Subsequent fixes are flagged
   as "post-step" until the next clean session.
** TODO Plausibility checks at startup
   Refuse to compute fixes if wall time is before the build date or jumps
   more than 1 hour from the last persisted shutdown time. Surface a clear
   error to the operator.
** TODO NTP sync tracking
   Record the timestamp of the last successful NTP sync (or equivalent
   trusted source). Persist across reboots. Expose "seconds since last
   sync" to the fix pipeline.
** TODO Optional drift-rate learning
   When NTP is available, observe the offset trend over time and persist
   an estimated local oscillator drift rate (ppm). Off by default. When
   enabled and offline, apply the correction and widen the time-uncertainty
   estimate accordingly.
** TODO Per-fix time confidence
   Each emitted fix carries a time-uncertainty value (seconds, 1σ) derived
   from: time since last sync, drift-rate uncertainty, and any detected
   step events. Propagate into longitude uncertainty in the fix output.
** TODO RTC handling on embedded image
   Document RTC battery requirements for the Pi appliance. If no RTC,
   persist last-known-good time on clean shutdown and on every successful
   fix, and use that as the floor at next boot.
** TODO Stale leap-second table detection
   The bundled leap-second table has an expiration. If the table is older
   than a configurable threshold (default 12 months) and a new leap second
   may have been announced, raise time uncertainty accordingly.
   Additionally, embed an optional "next-known-leap-instant" field. When
   set and the current UTC is past that instant *but* the locally-known
   TAI−UTC offset hasn't incremented, escalate to a hard time-uncertainty
   warning (an announced leap second has occurred but our table doesn't
   include it). Update path: app store update for mobile,
   ~bris-cli update~ for embedded — same channel as almanac and star
   catalog, all shipped as a unified ~bris-data~ payload.

* Phase 2: Vision core (no platform code)
** DONE Image abstraction
   ~Frame { width, height, pixels, timestamp, exposure, intrinsics,
   source_path, source_rotation }~. Pipeline-internal pixels are
   u16 grayscale; color and bit-depth conversion happens at the
   I/O boundary. Optional ~source_rotation~ field records any
   load-time rotation applied (for capture pipelines that read
   sensor pixels in non-viewing orientation); default is no
   rotation, since phone JPEGs and conventional camera images are
   already in viewing orientation.
** PARTIAL Lens model + calibration
   Pinhole + Brown-Conrady distortion (k1, k2, k3, p1, p2). Calibration
   workflow: capture N frames of a printed checkerboard or use star
   field self-calibration. Persist intrinsics per-device. For shipped
   hardware, a factory-default calibration is baked into the image and
   the user calibration workflow overrides it.

   *Status:* model + undistortion math complete in
   ~bris-vision::lens~ (10 tests). Calibration *workflow* now also
   implemented in the new ~bris-calibrate~ crate: corner detection
   via the `chess-corners` ChESS detector + `calib-targets`
   chessboard extractor, parameter solve via `vision-calibration`'s
   planar-intrinsics workflow (Zhang's method + non-linear bundle
   adjustment), TOML persistence, and a quality diagnostic.
   Wired into the CLI as ~bris calibrate --frames <dir> --rows
   --cols --square-size-mm~. ~bris serve~ loads the persisted
   intrinsics via the config file's ~[camera] intrinsics = ...~
   field or ~--intrinsics PATH~ and refuses to apply a calibration
   recorded at a different resolution than the camera is currently
   producing. Operator-facing user documentation in
   [[file:docs/operator/calibration.md][docs/operator/calibration.md]].

   *Interactive calibration UX (2026-05):* the per-frame primitive
   ~detect_corners_in_jpeg~ now reports a typed ~FrameOutcome~
   enum (Detected / NoBoardFound / WrongGridSize / DecodeFailed,
   with corner counts, bbox, and Laplacian-variance sharpness
   for the success case) so callers can show per-capture
   feedback instead of discovering bad frames only after the
   solve runs. The CLI walks the directory printing inline
   per-frame skip reasons during detection, an ASCII coverage
   map (4×4 grid of FOV cells with sample counts) before the
   solve, and a "worst-N per-view residuals" table after.
   ~CalibrationResult~ now carries per-view RMS / max
   residuals, a ~DetectionStats~ summary, and the ~Diagnosis~
   inline. The Android shell uses the new FFI surfaces
   (~detectCalibrationFrame~, ~calibrationCoverage~) to show
   per-capture chips (green/amber/red), auto-reject ~NoBoard~
   frames into ~frames/rejected/~, and render post-solve
   diagnosis cards plus worst-3 outlier views. Pose-coverage
   estimator lives in ~bris-calibrate::coverage~ as a
   pre-solve "where to point next" helper (heuristic, see
   module docs).

   Star-field self-calibration is still pending — interesting once
   plate solving on real data is reliable enough to bootstrap.

   *Factory profiles (2026-05):* the Android shell now carries a
   per-device factory-calibration registry
   (~FactoryCalibration.kt~) keyed by
   (~Build.MODEL~, lens id, capture resolution). When the
   operator hasn't run their own calibration, the live screen
   falls back to a matching factory entry before degrading to
   placeholder; the diagnostic overlay tags it
   ~calib: factory (<label>, rms <value>)~ so the operator
   knows it's a shipped default they can override. Initial
   entry: Cat S62 main camera @ 4032×3024
   (RMS 0.73 px, 15 views, diagnosis OK). Adding more
   devices is a one-entry-per-(device, lens, resolution)
   append to ~FactoryCalibration.PROFILES~. Star-field
   self-calibration and per-unit hardware factory profiles
   (vs per-model) remain follow-ups.
** TODO Eye-height handling
   Eye height contributes to horizon dip, which is a per-fix correction.
   - Persist a default eye height per device (settings).
   - Mobile: prompt at session start with the default prefilled, one tap
     to accept, swipe to adjust.
   - Embedded: configured once in ~/etc/bris/config.toml~.
   - Track eye-height *uncertainty* (default ±0.5 m) which feeds dip
     uncertainty in the error budget. Users in significant seas can
     widen the uncertainty manually.
   - Settings explainer: in significant seas, effective eye height
     ≈ standing height + ½ × dominant wave height + cockpit-above-water
     height. Document but do not compute — too many unknowns.
** DONE Horizon detection
   Three detection strategies, complementary across scene types:

   1. ~detect_horizon~ (classical: downsample → vertical gradient
      → RANSAC). Best for open-ocean scenes where the sea-sky
      boundary is the dominant horizontal edge. Fooled by deck/sail
      edges in cluttered shipboard scenes.

   2. ~detect_horizon_via_sky_region~ (classical: threshold + largest
      sky-touching connected component → take its lower boundary →
      RANSAC). Slightly better in cluttered scenes than the gradient
      detector but still fails when the sky region is bounded by a
      sail edge rather than the sea.

   3. ~detect_horizon_via_segmentation~ (ML: SegFormer-B0 finetuned
      on ADE20K, 14.5 MB ONNX, ~100 ms/frame inference via ort).
      Per-pixel sky / sea / boat / ship classification → take per-
      column sky→sea transitions, skip vessel-occluded columns →
      RANSAC. Robust against the deck-occluded sailing-camera case.
      Requires the ~segmentation~ feature flag (on by default;
      adds ~50 MB ONNX Runtime native lib to the binary).

   Return low-confidence fits explicitly via [`HorizonError`] so the
   operator can reject the sight rather than silently producing a
   bad fix.
** TODO Train a Bris-specific segmentation model
   The current pretrained model (SegFormer-B0 / ADE20K) was not
   trained on marine imagery and carries 150 classes (148 of which
   we ignore). A Bris-specific model would be better on every axis
   that matters.

   *Goals (in priority order)*:
   1. Smaller. Target ~1-5 MB (vs 14.5 MB) by reducing class count
      and using a smaller backbone (MobileNetV3-Small, EfficientNet-
      Lite, or a hand-designed small UNet). At small enough sizes
      we can plausibly run with ~tract~ instead of ~ort~, dropping
      the ~50 MB ONNX Runtime native dependency.
   2. Domain-accurate. Trained on real Bris-target footage (deck-
      mounted, hand-held, varied sea/sky/light conditions) instead
      of generic urban-and-indoor ADE20K imagery. Models that have
      never seen a sailing scene generalize less well to one.
   3. Smarter class set. The 4 classes we actually need:
      - ~sky~ (anything above the horizon line).
      - ~sea~ (open water below the horizon line).
      - ~vessel~ (the boat we're standing on, which we want to
        mask out so we don't measure to its edge).
      - ~obstruction~ (clouds, distant land, other vessels, sun
        glare on water — anything that interrupts a clean
        sky-to-sea transition).
   4. Robust to non-binary horizons (Phase 2 follow-up): a thin
      strip of distant shore between sea and sky should be
      classified as ~obstruction~ but tolerated — the horizon line
      is the bottom of the obstruction, not the bottom of the sky
      proper. The annotation guidelines need to handle this case
      explicitly.

   *Training data*. Three sources, in increasing order of relevance:
   - Public marine datasets: MaSTr1325 (Slovenian USV imagery, ~1325
     stereo pairs, sky/water/obstacle), MariShip, Singapore Maritime
     Dataset. Free, immediately available.
   - Bris field captures: a regression-test corpus of frames
     contributed by users (with consent) and labeled by us. The
     regression-test corpus described elsewhere in this plan
     doubles as training data once we have ~100+ frames.
   - Synthetic frames generated by combining marine-photo libraries
     with rendered boat models at varied camera angles. Useful for
     covering edge cases (specific vessel types, extreme weather)
     that natural collection misses.

   *Training pipeline*. Python + PyTorch in ~scripts/~. Reproducible
   from a vendored config. Output: ONNX file shippable via the
   ~bris-data~ OTA channel. Validation: tested against the
   regression-test corpus before each release; F1 score per class
   tracked over time.

   *Ship and update path*. Bris-data OTA channel carries the model
   weights alongside the leap-second table, almanac coefficients,
   and star catalog. Updating the model is operationally identical
   to refreshing any other reference data.
** TODO ML-assisted classical detection: catalog of opportunities
   The segmentation-based horizon detector is one application of ML;
   there are several more places where the ML output can *assist* a
   classical detector rather than *replace* it. Catalog of ideas,
   with current implementation status:

   1. *(DONE)* *Vessel-mask the centroid search.* Implemented as
      ~centroid_brightest_body_in_mask~ + ~SegmentationMask::non_vessel_mask~.

   2. *(DONE, with caveat)* *Sky-mask the body search.* Implemented
      as ~SegmentationMask::sky_mask~ + the masked centroid above.
      *Caveat:* on real frames where the bright sky region near a
      saturated Sun has its own internal brightness gradient, the
      area-weighted centroid is biased toward the brighter side of
      the bright region, not the body's actual peak. Documented in
      the regression test for ~sailing_sun_upper_left~. The right
      fix is to use the peak detector inside the mask rather than
      the connected-component centroider — see the standalone TODO
      "Switch Sun/Moon centroiding to peak detection inside sky mask"
      below.

   3. *(DONE)* *Obstruction-aware horizon RANSAC.* Implemented as
      ~sky_to_sea_transitions_with_obstruction~ with a ~CandidateSource~
      enum (SkyToSea / SkyToObstructionToSea / SkyToObstructionOnly).
      The detector accepts SkyToSea + SkyToObstructionToSea by
      default; SkyToObstructionOnly is filtered out. Empirical:
      on the ~sailing_with_distant_shore~ regression scene, the
      obstruction-aware variant adds 168 distant-shore candidate
      columns to the 162 clean sky→sea columns, doubling the
      available horizon evidence. *Future work:* weighted RANSAC
      that prefers SkyToSea over SkyToObstructionToSea, with the
      latter's σ contribution inflated to reflect its lower
      confidence. The current implementation treats both sources
      identically.

   4. *Star-region prior for night.* A trained model that identifies
      "this region of the image looks like night sky with stars" can
      bound the search area for the peak detector and suppress false
      stars from light pollution, ship lights, and reflections.

   5. *Plate-solve confidence prior.* An ML "is this region the night
      sky?" classifier can decide whether plate-solving is worth
      attempting on a given frame at all (vs. day fallback or "no
      sights possible right now").

   6. *Day/night/dawn/dusk classification.* A tiny image classifier
      (or even a percentile-based luma heuristic with ML refinement)
      that decides which detection regime to invoke. Wall clock can
      tell us roughly which phase we're in; the image can confirm or
      refine. Dawn/dusk is the genuinely hard regime — sky is bright
      enough to obscure most stars but dark enough that the Sun is
      not yet/no-longer the dominant feature.

   7. *Cloud-edge rejection in star detection.* Cloud edges look like
      bright peaks to the LoG-style detector. An ML cloud mask flags
      these regions so peak detection can ignore or down-weight them.

   8. *Per-frame quality score.* A learned model that predicts "this
      frame is likely to produce a good fix" before running the rest
      of the pipeline. Saves CPU on hopeless frames during a sweep.
      Inputs: brightness statistics, segmentation mask classes
      present, blur estimate, etc.

   9. *Lens distortion estimation.* A classical calibration workflow
      requires a checkerboard. An ML model trained on labeled
      "this lens has these distortion parameters" pairs could
      estimate intrinsics from a single sky/horizon frame, useful
      as a fallback when no calibration is available. Lower
      accuracy than a real calibration but better than the
      placeholder defaults.

   10. *Sea-state classification.* Wave height and orientation matter
       for the eye-height correction. A small classifier that
       estimates rough sea-state from a frame ("calm / moderate /
       rough") can inflate the horizon-dip σ contribution
       appropriately.

   These are all *additive* — they layer on top of the classical
   pipeline rather than replacing it. Bris stays interpretable: when
   it produces a wrong fix, the operator (or developer) can trace
   exactly which classical algorithm processed which (ML-flagged)
   region and what its inputs were. The honest-uncertainty invariant
   is preserved because each ML stage adds a σ contribution
   reflecting its own confidence.

   Items 1-3 are now done. Items 4-10 remain as future work.

   Constraining the saturated centroider to the sky mask
   therefore *excludes* the actual Sun pixels. The unmasked
   saturated centroider is the recommended path; saturation
   thresholding alone is restrictive enough to exclude most non-
   body pixels. The mask remains useful when there are multiple
   saturated regions (sail glare, water glare) but is not the
   default mode for Sun/Moon.

   The original peak-detection-inside-sky-mask idea remains valid
   for *non-saturated* bodies (the dusk Moon in
   ~marina_with_body~, dim planets, etc.). The peak detector is
   exercised against ~marina_with_body~'s rigging-occluded Moon;
   the future streaming engine should pick the appropriate
   detector based on body type and frame conditions.

** DONE Multi-frame stitching

   With a telephoto lens (which we need for sub-arcmin accuracy at
   the 0.5 nm target), the body and the horizon cannot fit in a single
   frame for any altitude above the lens's vertical FOV. The pose chain
   between frames is what relates the body's pixel position to the

     rate-table data on mechanical mounts, or the body's predicted

     to compute the body-to-horizon angle across the panorama.
   - Track per-frame timestamps; correct for the body's sidereal motion
     between frames so we don't smear a moving target.

** Per-stage resolution architecture
   Different pipeline stages have different optimal input
   resolutions. Centroiding precision scales with pixel count
   (sub-pixel fit on a saturated body benefits from every
   extra pixel); horizon-line fitting saturates at low
   resolution (the gradient SNR is the limit, not the pixel
   grid); segmentation gets *worse* above its training
   resolution (the deep features no longer match the
   receptive field); plate solving wants full resolution for
   peak detection but operates in resolution-free angle
   space afterward.

   Today's pipeline runs every stage on the same input frame.
   Operator picks one resolution at the camera, every stage
   sees that. The architecture below carves out per-stage
   downsampling so each stage operates at its preferred
   resolution while still composing into a single fix.

   Discussed with the operator (May 2026 session); broken
   into four steps committed independently so each is
   reviewable in isolation. Steps 1-3a landed; 3b + 4 pending.

*** DONE Step 2: Camera-space ray output types
    New ~bris_vision::ray~ module:

    - ~CameraRay~ — unit 3-vector in the camera frame (+x
      right, +y down, +z toward scene). ~from_pixel(intr, x,
      y)~ for the standard lens-model conversion.

*** DONE Step 5: Capture at native sensor maximum
    The per-stage architecture's whole point was to let
    stages that benefit from higher resolution (centroiding,
    plate-solve) see all the pixels the sensor can deliver
    while stages that prefer lower resolution (horizon,
    segmentation) downsample on their own via ~FramePyramid~.
    With steps 1-4 + follow-ups landed, the downstream
    plumbing supports it. But capture itself was still
    hardcoded to 1280×720 on both Android (~CameraConstants~)
    and Linux (CLI default 640×480), which defeated the
    architecture: every stage saw at most 720p regardless of
    sensor capability.

    Capture now requests the chosen lens's *native maximum*
    on both platforms:

    - *Android* (~CameraConstants.maxOutputSizeFor(context,
      cameraId)~): queries ~StreamConfigurationMap~ for the
      largest ~ImageFormat.YUV_420_888~ output size the
      physical camera advertises. Calibration uses the same
      lookup, so calibration intrinsics and live-fix
      intrinsics match exactly (no scaled_to round-trip
      needed at the boundary). The old ~CameraConstants.WIDTH~
      / ~HEIGHT~ / ~SIZE~ constants are gone; consumers pass
      the resolved ~Size~ through.

    - *Linux / V4L2* (~bris_capture::max_yuyv_resolution~):
      new free function that enumerates YUYV frame sizes via
      ~VIDIOC_ENUM_FRAMESIZES~ and picks the largest. The
      CLI's ~ResolvedServeConfig~ / ~ResolvedCaptureConfig~
      drop their silent 640×480 default; ~width~ / ~height~
      are now ~Option<u32>~ and the resolver returns ~None~
      when neither CLI nor config-file specifies them. The
      CLI's ~resolve_capture_resolution~ helper then queries
      the device at open time.

    *Throughput trade-off — accepted by the operator:*
    higher capture resolution means the single-threaded
    streaming engine takes longer per-frame; ~STRATEGY_KEEP_ONLY_LATEST~
    on the Android side and the engine's input ring on
    both sides drop excess frames cleanly. *Lower fix
    cadence at higher resolution is the preferred trade* —
    a 5-second-per-fix cadence at full sensor resolution
    beats a 1-second-per-fix cadence at 720p because the σ
    on each fix is what drives the 0.5 nm position target.

** DONE Night-horizon detection v1: sea-sky luma boundary
   ~bris-vision::night_horizon~ implements the sea-sky luma
   boundary approach. Works on the smoothed *per-row* mean luma
   profile rather than per-column gradients:
   1. Per-row mean luma over a horizontal center band, optionally
      honoring a column mask (essential when a saturated body is
      present — must also be excluded from row-mean computation,
      not just from candidate generation).
   2. Smooth with a small box filter.
   3. Find the row of maximum vertical gradient in the configured
      ~search_row_range~.
   4. For each column, find the row in a window around the global
      horizon row where per-column gradient is largest.
   5. RANSAC-fit through the candidates.

   Convenience function ~detect_horizon_night_excluding_body~
   builds both the column mask AND restricts ~search_row_range~
   to "below the body."

   *Empirical results on the night corpus:*
   - ~night_test_lowres~ (moonlit; portrait 1080×1920): default
     config catches the moon halo's edge at y ≈ 258. With
     manually-tuned ~search_row_range = (0.55, 1.0)~ +
     ~min_inlier_fraction = 0.2~, finds the actual sea-sky
     horizon at y ≈ 1324 (~69% of frame height).
   - ~night_test_highres~ (stars over wake): finds y=180
     (wake-region transition), not the actual y=85 horizon.
     Segmentation detector handles this scene better.
   - ~container_ship_night~, ~container_ship_night_lights_on_water~:
     finds the deck-to-sky boundary, not the sea-sky horizon.

   The detector finds the **strongest horizontal luma transition**
   in the search range, which is sometimes the horizon and
   sometimes a deck/wake/halo edge. The follow-up tasks below
   address the disambiguation problem.

   *Caveat from corpus probing:* on daylight scenes the peak
   detector subtracts a local background (33×33 box mean), which
   means the saturated Sun against bright haze produces a low
   foreground signal and doesn't appear as a top peak. This is
   the right behavior for star detection (where the background is
   dark sky and stars stand out by absolute brightness), but means
   the peak detector is *not* a substitute for the saturated-body
   centroider on daylight Sun/Moon scenes.

** DONE Geometric hash database
   Implemented in ~bris-platesolve::hash::StarHashDb~. For each
   catalog star (anchor), enumerates 4-tuples consisting of the
   anchor + 3 of its M nearest neighbors within
   ~max_pattern_diameter_rad~. Computes a quantized hash from the
   6 pairwise distances of the 4-tuple (sort, normalize by
   largest, quantize the 4 smaller ratios into ~bin_count~ bins
   each). Inserts into ~HashMap<hash, Vec<CatalogPattern>>~.

   The neighborhood approach (~O(N · M^3)~) is essential: naïve
   ~O(N^4)~ enumeration is intractable at the catalog densities
   Bris targets — mag 4.0 = ~500 stars = 2.6×10^10 4-tuples.
   With ~neighbor_limit M = 20~ and mag cutoff 4.0, the database
   has ~1M patterns and builds in well under a minute in release
   mode.

   Lookup probes the exact bin plus its 8 ±1-in-one-dimension
   neighbors to handle quantization-edge cases.

   Build is lazy at first call; not yet serialized via build.rs.
   For the ~10s-30s release-mode build cost on full mag-5.5
   catalog, consider a build.rs path later if startup latency
   matters.

** DONE Matcher
   Implemented in ~bris-platesolve::solve::plate_solve~. Pipeline:

   1. Map each detected peak to a unit ray in camera frame using
      the camera's intrinsics.
   2. Enumerate 4-tuples of the brightest N peaks (default 12),
      compute the hash from the 6 pairwise angular distances, look
      up matching catalog patterns.
   3. For each candidate (peak 4-tuple, catalog 4-tuple) pair,
      try all 24 permutations of star ↔ peak assignment. Run
      Kabsch (closed-form least-squares rotation) to get an
      attitude.
   4. Verify by projecting *additional* catalog stars within the
      candidate FOV into the camera frame and counting how many
      land near a detected peak. Enforces one-to-one peak ↔ star
      matching to avoid the false-positive trap where multiple
      catalog stars collapse onto the same peak.
   5. Return the highest-verification-count match if it exceeds
      a confidence threshold.

   Kabsch implemented via Jacobi-rotation SVD on a 3×3 matrix —
   no external linear-algebra dependency. Handles the reflection
   case correctly. ~50 lines of straightforward numerical code.

   *Validated end-to-end* via the synthetic round-trip test
   (~round_trip_recovers_known_attitude~, ~#[ignore]~ for slow
   debug runs): builds a mag-4.0 db, picks a known sky region,
   constructs a known attitude, projects all in-cone stars
   through it to synthesize peaks, runs the solver, verifies the
   recovered attitude maps the aim point near +Z. Passes in
   release mode in ~30s.

   *Real-data probes* (~tests/real_data.rs~,
   ~#[ignore]~) demonstrate the solver runs end-to-end on
   ~night_test_highres~ and ~container_ship_night~. Whether the
   matched sky region is the *correct* one is a separate question
   that requires either:
     - Tighter verification (sub-pixel residual RANSAC instead of
       a 1° verify radius).
     - External priors (observer location + capture time + IMU)
       to constrain candidate sky regions geometrically.

** DONE Verification refinement to reduce false matches
   Implemented as a refinement step in ~try_verify~: after the
   loose-radius (1°) verification loop produces a candidate
   (initial 4 + verified-N) match, re-run Kabsch on all matched
   pairs and compute the RMS angular residual under the refined
   rotation. Reject the match if the RMS exceeds
   ~max_rms_residual_rad~ (default 30 arcsec).

   *Empirical impact:* on ~night_test_highres~ the v1 returned a
   12-star "match" in the southern hemisphere; refinement
   correctly rejects it as a false-positive. With placeholder
   intrinsics the *correct* sky region also fails refinement
   (residuals can't be sub-arcmin when the pixel→ray mapping is
   wrong by 2-3×), so the post-refinement behavior on real
   footage is "no match returned" until calibration arrives.

   Also enforced one-to-one peak↔star matching in the
   verification loop (separate fix in commit a33ddea): without
   it, the loose-radius verifier accepted multiple catalog stars
   matching the same peak, inflating verification counts.

   Two follow-ups remain (less critical now that refinement is
   in place):
   - Magnitude consistency check.
   - External prior (observer location + time) to constrain
     candidate sky regions geometrically.

** DONE Lens selection (multi-camera Android devices)
   Modern phones expose multiple physical cameras (ultrawide,
   wide, telephoto) through CameraX's logical-camera API. The
   wide lens is the default; the **telephoto** is what Bris
   actually wants — more arcsec-per-pixel at the body
   centroid means tighter altitude σ, exactly the win the
   accuracy section of ~readme.org~ calls out.

   Surface:
   - Settings → Camera → Lens: radio between "Wide (1×)" and
     "Telephoto (Nx)" plus any additional physical cameras
     the device exposes. Enumerate via
     ~Camera2CameraInfo.from(info).cameraCharacteristicsMap~,
     identify telephoto by the longest ~LENS_FOCAL_LENGTHS~
     entry.
   - LiveScreen + CalibrationScreen pin the chosen lens via
     ~CameraSelector.Builder().addCameraFilter { ... }~
     filtering to the selected physical camera ID.
   - Calibration storage extends with a ~lens_id~ key:
     ~<external-files>/calibration/<lens-id>/<resolution>/<session-ulid>/...~
     so a calibration solved against the wide lens doesn't
     accidentally apply to the telephoto. The on-device
     intrinsics-loader keys by ~(lens_id, width, height)~.
   - First-launch default per device: pick the lens with the
     longest focal length that delivers reasonable low-light
     performance (heuristic: prefer non-ultrawide lenses
     with sensor area ≥ 1/3" if available; otherwise the wide
     default).

   Cross-references:
   - The accuracy framing in ~readme.org~ §"What the operator
     can do" item 2 ("Use a long focal length") is the
     architectural rationale.
   - Telephoto FOV is small enough that body-and-horizon
     rarely fit in one frame above modest altitudes, which
     pushes the multi-frame stitching path
     (~bris-vision::panorama~ + the streaming engine's
     cross-frame pair-selection logic) into the common case
     rather than the edge case. That path is implemented but
     gets exercised more.

* Phase 8.5: Build provenance & version stamping (testing-revamp prerequisite)
  Every captured bundle and every replayed sight/fix must be
  reconstructible back to the exact engine code that produced it.
  Today nothing in `bundle.json` lets us do this: `device.app_version`
  is a hand-edited `"0.1.0"` in `bris-android/app/build.gradle.kts`,
  `bris-ffi::version()` returns the workspace `Cargo.toml` semver
  (`"0.0.1"`), the reserved `build_timestamp_utc` is hardcoded
  `None`, and no git SHA is captured anywhere. Two bundles stamped
  `"0.1.0"` could be a hundred commits apart.

  This phase is a prerequisite for the testing-strategy revamp: the
  regression corpus is worthless if we can't pin a sight to the
  engine code that emitted it.
** TODO `bris-ffi` build script captures git provenance
   `build.rs` shells out to `git rev-parse HEAD`,
   `git describe --dirty --always --tags`, and `git rev-list --count
   HEAD`. Exposes them as env vars (`BRIS_GIT_SHA`,
   `BRIS_GIT_DESCRIBE`, `BRIS_GIT_DIRTY`, `BRIS_GIT_COMMIT_COUNT`,
   `BRIS_BUILD_TIMESTAMP`) consumed via `env!`. Hand-rolled (~30
   lines, zero deps); reject `vergen` to avoid pulling `git2`.
** TODO Extend `VersionInfo` across the FFI
   Add `git_sha`, `git_describe`, `git_dirty: bool`, `commit_count`,
   `build_timestamp_utc` to `bris_ffi::VersionInfo`. Existing
   `bris_ffi` semver field stays as the workspace semver. Document
   the FFI surface change in the bindings.

   Additive within `schema_version: 1`. New struct on
